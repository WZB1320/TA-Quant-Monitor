## 三、这个基线为什么可信

### 3.1 数据被冻结，不随后续改造漂移

复权改造会改写 `data/kline_cache.db`（补 hfq / raw、重抓统一批次），届时"改造前"的原数据就不存在了。
因此基线用的不是主库，而是**冻结快照**：

```
data/baseline_snapshot_20261016.db   ← 主库在改造前的完整副本（40130 行）
```

### 3.2 没有触发任何远程抓取

这是本次最关键的一点。`run_backtest.py` 直接跑会出问题：

- 它调用 `get_daily_kline(code, start_date='2024-07-01')` **不传 `end_date`**
- `end_date` 默认为今天（2026-10-16），而缓存末日是 2026-09-28
- `DataManager` 判定缓存过期 → **对 35 只标的全量远程重抓**
- 结果：所有标的的 qfq 基准被推进到 10-16 时点

也就是说，**直接跑一次基线，基线本身就变了**，之后再对比就失去意义。

基线脚本的做法：
- `end_date` 显式锁 `2026-09-28`（= 缓存末日），缓存新鲜度判定必然命中
- `dm._source_order = []` 禁用全部远程源，作为第二道保险——即使日期传错也是报错而非静默联网

### 3.3 零污染

运行前后核对：

| 对象 | 运行前 | 运行后 | 结论 |
|---|---|---|---|
| 主库 `kline_cache.db` 行数 | 40130 | 40130 | 未变 |
| 主库批次分布 | 9 批次 | 9 批次 | 未变 |
| `strategy_memory_*.jsonl` mtime | Sep 29 | Sep 29 | 未写 |
| `signal_history.json` mtime | Sep 29 | Sep 29 | 未写 |
| `backtest_memory/` run 数 | 362 | 362 | 未新增 |

（`RuntimeMode.BACKTEST` 在导入回测层前设置，`SignalFilter` 不落盘。）

### 3.4 可复现性：双跑 bit-for-bit 一致

同一脚本在**两个独立进程**各跑一次（约 6 分钟/次），逐字段比对：

| 校验项 | 结果 |
|---|---|
| headline 12 项指标（浮点全精度） | **全部 SAME** |
| 229 笔交易逐笔比对 | **0 处差异** |
| 分组统计 | 完全一致 |
| 数据指纹（逐标的 close sha256） | 完全一致 |

`backtest_baseline_20261016-rerun.json` 保留作为该结论的证据。

## 四、基线数据本身的已知缺陷（改造对照时须记账）

**35/35 标的的历史都是跨批次拼接的**（100%，不是此前统计的部分标的）：

| 批次组合 | 标的数 |
|---|---:|
| `2026-08-07 + 2026-09-28 + 2026-09-29` | 33 |
| `2026-09-28 + 2026-09-29` | 2 |

即每只标的的价格序列由 2~3 个**不同抓取时点**的 qfq 切片首尾相接而成。
每批次的 qfq 基准不同（后续分红会把早段价格追溯性压低），因此：

- 同一条序列内部存在**微小的系统性台阶**（此前实测：茅台三个月被重定价 −2.31%，且均匀无阶梯）
- 不同标的之间的绝对价格**不可横向比较**（各自的基准时点不同）
- 这对 229 笔交易的收益有直接影响，方向是**系统性虚增**

对照实验建议：改造后对比时，**必须区分两种变化来源**——
(a) 复权口径修正带来的真实变化；(b) 批次基准统一带来的漂移修正。
若要隔离二者，需要额外做一次「仅统一批次、不改复权」的中间态回测。

## 五、使用方法

重跑基线（会覆盖同名输出，或用新 tag 侧写）：

```bash
python scripts/run_baseline_backtest.py            # tag = 当天日期
python scripts/run_baseline_backtest.py mytag      # 指定 tag
```

改造完成后，用**同一份快照数据**跑改造版回测，对比三组数字：
总收益率 / 最大回撤 / 交易笔数，以及逐笔交易的 `entry_price`、`exit_price`、`pnl` 差异。
